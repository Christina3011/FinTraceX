# FinTraceX: Real-Time Financial Fraud Intelligence

**HackNex 2026, Internal Qualifier. Problem statement HNX26PSI04.**
Team: _<add team name and member names>_

FinTraceX scores every transaction and account for fraud risk, explains flagged transactions in plain English, finds **fraud rings** (groups of accounts acting together) with a graph, and recommends an action for each.

---

## What the project does

Fraud often hides in patterns across many accounts rather than in one suspicious transaction. FinTraceX:

1. Builds behaviour features for each transaction (for example, amount compared with the account's normal, new device, hour of day).
2. Scores each transaction with an **XGBoost** model (risk from 0 to 1).
3. Explains each flagged transaction with **SHAP**, converted to plain English, e.g. *"unusual item (gift_card); unusual hour (03:00)"*. Unflagged transactions have an empty reason.
4. Builds a **graph** of accounts, devices and payout accounts and finds groups that act together.
5. Keeps a group as a ring only if at least 2 of 3 signals hold, helping distinguish suspicious groups from families or offices that share a device.
6. Gives each account a final score, a reason and a recommended action.
7. Saves all results as files in `outputs/` (CSV, JSON and an HTML connection diagram) for the frontend to display.

| Required output (from the problem statement) | Where to find it |
|---|---|
| Risk score per transaction | `outputs/scores.csv` |
| Risk score per account | `outputs/accounts_final.csv` |
| Accounts that are suspicious together | `outputs/rings.json` |

## Technologies, libraries and models

| Purpose | Tool |
|---|---|
| Language | Python 3.10+ |
| Data | pandas, numpy |
| Risk model | **XGBoost** (gradient-boosted trees) |
| Baseline for comparison | Logistic Regression (scikit-learn) |
| Explanations | SHAP values from XGBoost (`pred_contribs`) |
| Graph and ring detection | networkx |
| Diagram | pyvis |

**Why XGBoost:** it is accurate on tabular data, handles rare fraud with `scale_pos_weight`, gives exact SHAP explanations, and trains in seconds without a GPU.

## Reproducing the results

The simulation uses a fixed seed, so running the commands above on the same package versions reproduces the same dataset. Model scores can vary very slightly between XGBoost versions, so small differences in the counts below are normal. The ring result should be the same.

## Data pipeline

```
simulate_data.py  ->  data/transactions.csv  (+ ground_truth.json, evaluation labels)
features.py       ->  per-transaction features
train.py          -> XGBoost scores, threshold, SHAP reasons   -> outputs/scores.csv,
                                                                   account_scores.csv, model.json
rings.py          ->  graph, rings, account actions, diagram    -> outputs/rings.json,
                                                                   accounts_final.csv, ring_graph.html
```

### What the simulated data contains
- 510 accounts and 12,575 transactions, with about 1.65% fraud
- **One fraud ring:** 10 accounts sharing 3 devices, buying the same items in the same order, then paying out to one account
- **40 lone fraud accounts:** stolen-card style (large amount, new device, new city, 1 to 4 AM)
- **30 legitimate high-value purchases** (laptops, phones, TVs) used to measure false positives
- **18 innocent shared-device groups** (15 families and 3 offices) to test for false rings

### Features used by the model
Amount compared with the account's previous average, hour of day, new device, new location, transactions in the last hour, number of accounts sharing the device, number of accounts sharing the payout account, plus merchant, item and location.
`account_id` and `txn_id` are never given to the model.

### Method details
- **Train, validation and test sets are split by account**, so no account appears in two sets.
- **Threshold** is chosen on the validation set: the highest recall that keeps precision at 90% or more. If no threshold meets that target, the script falls back to the best F0.5 score.
- **Ring rule:** a group of 3 or more accounts linked by shared devices or payout accounts is a ring only if at least 2 of these hold: (1) at least half of the members have flagged transactions, (2) the members share a payout account, (3) at least 3 members follow the same sequence of flagged purchases.
- **Account risk:** `train.py` writes an auxiliary account score as the mean of the top three transaction scores. `rings.py` writes the final account score as the highest transaction score.

**Recommended action:** FREEZE all member accounts and investigate; block the payout account.

## Limitations

- Results are on simulated data only. Real data would be noisier.
- The ring is easy to find because it has strong shared-device and shared-payout signals. Fraudsters who spread over many devices would be harder to catch.
- A few legitimate high-value purchases are still flagged. Raising `MIN_PRECISION` in `train.py` may reduce this at the cost of some recall.
- The model is trained on labelled fraud, so brand-new fraud types that look different would be missed. An unsupervised detector (Isolation Forest) would help and is listed as future work.
